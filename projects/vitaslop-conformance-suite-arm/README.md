# vitaslop-conformance-suite-arm

> Keep this README terse: sectioned and bulleted, not large prose. Explain
> concepts and the why, not exact type names. Update it as the code changes so it
> never goes stale.

A generic ARM conformance corpus: one small program per file, with a seed state
and a golden result. **No vitaslop dependency** - anyone building an ARM core can
run it from this file. The Rust lib is an optional convenience for Rust harnesses
and mirrors what is written here; **this README is the format's source of truth.**

## Human half / generated half

Each case file is split by a marker line, `# --- generated by regen; do not edit
below this line ---`.

- **Above**: what is being tested and why, the `asm`, the seed registers, the
  mode switches. The part a person reviews.
- **Below**: the assembled bytes and the observed golden, written by `regen` from
  an `as` + qemu oracle.

**A golden is never authored by hand.** A hand-computed expectation encodes the
author's belief about the architecture, which is the belief under test - if the
implementation and the test share a misreading, both are wrong and the suite is
green. `regen` rewrites only the lower half, deterministically, so an unchanged
case produces no diff.

## Fields

| Key | Half | Meaning |
| --- | --- | --- |
| `description` | human | What this exercises, and which values are interesting. |
| `asm` | human | GNU `as` source, assembled at 0 as a flat binary. |
| `mode` | human | `arm` (default) or `thumb`. |
| `capture` | human | `regs` (default) or `output`. |
| `[in].regs` | human | Seed registers; unlisted starts at 0. |
| `[bin].base64` | generated | The flat binary, base64, wrapped at 80 columns. |
| `[out.regs]`, `[out.flags]` | generated | `regs`: final `r0..r12`, `r14`, and NZCV. |
| `[out].output` | generated | `output`: the bytes the program wrote to the host. |

## Running a case

- Load `[bin]` at 0, start at 0 in `mode`, zero the registers, apply `[in].regs`,
  clear the flags, run to exit, compare.
- `regs` omits zero registers, so **absent means 0, not "don't care"** - else a
  case that wrongly clears a register passes. `r13`/`r15` are not captured: they
  reflect how the harness set things up, not what the instruction did.
- `output` is the whole-program shape (address formation, memory, host seam,
  exit) that registers cannot reach. Programs use the Linux EABI convention:
  `svc #0`, number in `r7` (`4` write, `1` exit).
- A case missing its generated half is an **error, not a skip** - a suite that
  skips reports green for work it did not do.

## Regenerating

- `regen` assembles and runs each case under qemu. Toolchain and qemu come from
  `PATH`, overridable with `ARM_AS`, `ARM_OBJCOPY`, `ARM_LD`, `QEMU`. From a
  Windows checkout, run it inside WSL.
- qemu is a strict **black-box oracle**: executed and observed, never read,
  linked, or derived from.

## Note

- The cases are also embedded at compile time, so the corpus runs where there is
  no filesystem - the browser runner executes the exact same committed files as
  the native path, which is what makes the two engines comparable.
